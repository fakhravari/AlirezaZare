# قرارداد مستندسازی مخزن

راهنمای هر قابلیت باید در پوشهٔ حوزهٔ خودش قرار بگیرد. قواعد بالادستی در [AGENTS.md ریشه](../../AGENTS.md) و روند روزمره در [docs/AGENTS.md](../AGENTS.md) هستند.

## نقشهٔ محل‌ها

| حوزه | محل |
|---|---|
| ساختار، route، داده و دیتابیس | `docs/architecture/` |
| layout، CSS، JS و UI مشترک | `docs/frontend/` |
| محصول، کاتالوگ، سبد و پرداخت | `docs/store/` |
| پروفایل و حساب | `docs/account/` |
| مجله و صفحات محتوایی | `docs/content/` |
| رسانه | `docs/media/` |
| SEO | `docs/seo/` |
| مدیریت | `docs/admin/` |
| اجرای پروژه، کیفیت و روند | `docs/development/` |

ریشهٔ `docs/` فقط `README.md` و `AGENTS.md` دارد. پیش از ساخت فایل، سند موجود را بررسی و در صورت هم‌پوشانی همان را اصلاح کنید. سند تازه باید مستقل، lowercase-kebab-case، در README بخش فهرست‌شده و از README اصلی قابل یافتن باشد.

## کیفیت محتوا

هر راهنما باید هدف، نقاط ورود واقعی در کد، رفتار فعلی، منبع حقیقت داده، وابستگی‌های مشترک و روش بررسی را روشن کند. نمونه/seed، localStorage، API و دادهٔ قطعی DB را جدا توصیف کنید. محدودیت محیطی را به قابلیت محصول تعمیم ندهید. قرارداد تکراری را در چند سند کپی نکنید؛ به مرجع واحد لینک دهید. کد جاری بر متن مستند مقدم است.

تاریخ را فقط وقتی ثبت کنید که همان مسیرها و رفتار با کد تطبیق داده شده‌اند. نتیجهٔ اجرای روی یک محیط را به همهٔ پایگاه‌ها تعمیم ندهید.

## اعتبارسنجی

```powershell
node docs/development/check-docs.mjs
git diff --check
```

checker وجود لینک محلی و ساختار/ناوبری را بررسی می‌کند؛ صحت معنایی و runtime را اثبات نمی‌کند. برای آن `npm run check` و بررسی‌های حوزه‌ای را طبق [کیفیت](quality.md) اجرا کنید.
