# قانون محل و نگهداری راهنماها

این قانون برای همهٔ تغییرهای مخزن اعمال می‌شود و از [AGENTS.md ریشه](../../AGENTS.md) و [روند عامل](../AGENTS.md) ارجاع دارد.

## قانون الزامی محل سند

**راهنمای هر بخش باید در پوشهٔ همان بخش در docs ایجاد یا به‌روز شود.** ریشهٔ docs فقط محل `README.md` برای فهرست و `AGENTS.md` برای روند مشترک است. راهنمای قابلیت، صفحه یا دارایی تازه را در ریشهٔ docs نسازید و به سند کلی نامرتبط اضافه نکنید.

| حوزهٔ تغییر | محل مرجع | نمونه |
|---|---|---|
| ساختار برنامه، route و مرز داده | `docs/architecture/` | routing.md، data-sources.md |
| layout، CSS، JS و قرارداد UI مشترک | `docs/frontend/` | layout.md، styling.md، javascript.md |
| محصول، فهرست، جستجو، مقایسه، سبد و تسویه | `docs/store/` | catalog.md، product.md، cart.md |
| پروفایل، آدرس و سفارش‌های حساب | `docs/account/` | profile.md |
| مجله، برند، خدمات، قوانین و هویت | `docs/content/` | pages.md |
| تصویر، پرچم، لوگو، ویدئو و فایل محتوا | `docs/media/` | images.md |
| metadata، canonical، schema و crawl | `docs/seo/` | metadata.md |
| اجرا، workflow، استاندارد مستندات و برنامهٔ آینده | `docs/development/` | setup.md، workflow.md، roadmap.md |

اگر راهنمای مرتبط وجود دارد، همان را کامل کنید. سند جدا را زمانی بسازید که موضوع مستقل و قابل ارجاع باشد. برای حوزه‌ای که در این گروه‌ها نمی‌گنجد، پوشهٔ معنادار lowercase-kebab-case با README بسازید و آن را در فهرست اصلی ثبت کنید؛ سند را موقتاً در ریشه رها نکنید.

## مرجع واحد و ارتباط بین بخش‌ها

- هر قرارداد یک محل اصلی دارد: جدول route در معماری، ترتیب asset در frontend/layout، event/storage در frontend/javascript، سبد در store/cart و ابعاد رسانه در media/images.
- راهنمای بخش مصرف‌کننده به قرارداد مشترک لینک می‌دهد؛ متن و جدول آن را کپی نمی‌کند. مثلاً راهنمای محصول برای ابعاد thumbnail به رسانه ارجاع می‌دهد.
- در تغییر چندحوزه‌ای، هر بخش فقط قسمت مسئول خودش را توضیح می‌دهد. indexها برای پیدا کردن راهنما هستند و نباید به سند جامع تازه تبدیل شوند.
- تفکیک docs مرز مسئولیت را نشان می‌دهد؛ وجود پوشه به معنی ایجاد service، API یا ماژول مستقل در کد نیست.

## ساختار و نام‌گذاری

1. سند با هدف، محدوده و نقاط ورود شروع شود؛ route/Controller/View/CSS/JS یا منبع دادهٔ مرتبط را مشخص کند.
2. رفتار پیاده‌شده، state و قراردادهای مهم را توضیح دهد؛ demo/localStorage را از backend واقعی متمایز کند.
3. روش بررسی متناسب، وابستگی به بخش مشترک و محدودیت شناخته‌شده را ثبت کند؛ از توضیح تاریخچهٔ مکالمه و کارهای رهاشده پرهیز شود.
4. به فایل کد واقعی و سند مرجع با لینک نسبی متصل شود؛ مسیر مطلق ماشین نویسنده و لینک file:// نسازید.
5. نام سندها lowercase-kebab-case با پسوند md باشد. `README.md` و `AGENTS.md` استثناهای قراردادی‌اند. نام فایل‌های پشتیبان سند نیز معنادار و در بخش خودش باشد.
6. هر بخش README دارد؛ هر راهنمای تازه در آن فهرست می‌شود و از فهرست اصلی قابل دسترسی می‌ماند. سند به README بخش و فهرست اصلی لینک برگشت داشته باشد.
7. تاریخ آخرین تطبیق با کد ثبت شود؛ snapshot ترتیب فایل یا اندازه را تضمین همیشگی معرفی نکنید. کد و runtime بر سند مقدم‌اند و اختلاف باید اصلاح شود.

از [الگوی راهنما](guide-template.md) برای سند جدید استفاده کنید. پیشنهادهای آینده و بدهی‌ها در [roadmap](roadmap.md) قرار می‌گیرند؛ از نوشتن آن‌ها به شکل قابلیت موجود پرهیز کنید.

## بررسی پیش از تحویل

```powershell
node docs/development/check-docs.mjs
git diff --check
```

[check-docs.mjs](check-docs.mjs) جای سند، نام فایل Markdown، README گروه‌ها، وجود مقصد لینک‌های محلی و دسترسی همهٔ راهنماها از README اصلی را بررسی می‌کند. ابزار anchorهای داخل صفحه، لینک خارجی، صحت معنایی متن، runtime و محتوای فایل کد را بررسی نمی‌کند؛ نویسنده همچنان باید راهنما را با تغییر واقعی تطبیق دهد.

پس از جابه‌جایی سند، همهٔ ارجاع‌های مسیر قبلی را در مخزن اصلاح کنید. فایل‌های عمومی قدیمی به راهنماهای موضوعی این ساختار منتقل شده‌اند؛ جزئیات جدید را دوباره در یک فایل جامع ریشه جمع نکنید.
