# بدهی‌ها و برنامهٔ پیشنهادی توسعه

این صفحه فهرست کارهای آینده است؛ موارد زیر قابلیت پیاده‌شده یا تعهد زمان‌بندی نیستند. وضعیت جاری معماری و داده در [نمای کلی](../architecture/overview.md) و [منابع داده](../architecture/data-sources.md) قرار دارد.

## بدهی‌های فعلی

- CSSها هنوز با مالکیت کاملاً انحصاری/namespace جدا نشده‌اند؛ `style.css` و `industrial-system.css` بزرگ و دارای overrideهای چندمرحله‌ای‌اند.
- توکن‌های legacy و canonical هم‌زمان حضور دارند؛ نام alias همیشه معنای ظاهری مورد انتظار را نمی‌رساند.
- مرزهای responsive هم‌پوشان‌اند و در چند فایل مقدارهای 380/389/390، 991/991.98/992 و مرزهای صفحه‌ای وجود دارد.
- بعضی CSS/JSها در مخزن هستند ولی از layout جاری load نمی‌شوند؛ قبل از فعال‌سازی یا حذف، ارجاع و runtime را بررسی کنید.
- `/profile/edit` فقط مسیر سازگاری است و به `/profile` هدایت می‌شود؛ View و CSS مستقل ندارد.
- catalog، profile/auth، favorite/compare، address، coupon و payment عمدتاً demo/localStorage هستند؛ به‌عنوان backend واقعی معرفی نشوند.
- solution پروژهٔ تست مستقل ندارد؛ مستندسازی/بازبینی runtime جای ادعای تست خودکار را نمی‌گیرد.
- سند باید با هر تغییر route، partial، ترتیب asset، event یا storage key به‌روز شود؛ اطلاعات منسوخ از راهنمای «کامل» بدتر است.
- خواندن brand-editorial در BrandsController از مسیر با حروف `Shop` به‌جای `shop`؛ پیش از استقرار روی فایل‌سیستم حساس به حروف اصلاح و بررسی شود.
- نشان «برق شیراز» و نام «ندا اولیائی» در چند لایه حضور دارند؛ هویت و تماس تنظیم مرکزی واحد ندارند.
- ProductSeoCatalog به ساختار متن catalog.js وابسته است؛ ترتیب ردیف نیز در شناسه و رسانه اثر می‌گذارد.

## مراحل پیشنهادی

### مرحلهٔ اول — تثبیت منبع UI

- کاهش cascade تکراری `style.css`/`industrial-system.css` و تعیین مالک واحد برای هر component مشترک.
- تکمیل توکن‌های semantic (surface, border, muted text, focus, status, icon) و مصرف آن‌ها در صفحه‌های فعلی.
- یکپارچه‌کردن قرارداد هدر، مگامنو، پنل‌ها و modal بین خانه و صفحات داخلی؛ سپس حذف استایل‌های تکراری فقط پس از visual regression.

### مرحلهٔ دوم — تثبیت داده و مرزهای دامنه

- تعریف مدل‌های دامنهٔ Product, Variant, Accessory, Cart, Order, Address, User و اعتبارسنجی سمت سرور.
- انتقال کاتالوگ از JavaScript به منبع backend و تعریف repository/service/API مناسب.
- جایگزینی شبیه‌سازی auth و سفارش با هویت و persistence واقعی، همراه با مجوزدهی و مدیریت خطا.
- مستندسازی قرارداد API و source-of-truth هر داده پیش از اتصال UI.

### مرحلهٔ سوم — کیفیت قابل‌تکرار

- افزودن تست‌های unit برای منطق دامنه و validation؛ integration tests برای routeها/API.
- افزودن smoke/e2e برای مسیر خرید، حساب و جستجو با viewport دسکتاپ و موبایل.
- بررسی دسترس‌پذیری (کیبورد، focus، screen reader، کنتراست)، RTL، overflow، و خطاهای console/network.
- ایجاد CI برای restore/build/test و کنترل کیفیت assetها.

### مرحلهٔ چهارم — نگهداری و بهینه‌سازی

- پس از ثبت پوشش و ارجاع‌ها، شناسایی فایل‌های بلااستفاده، duplicate/vendorها و استایل‌های legacy؛ حذف مرحله‌ای و قابل برگشت.
- بهینه‌سازی تصویر/فونت/ویدئو، caching و بارگذاری تنبل بر پایهٔ اندازه‌گیری واقعی.
- افزودن logging/monitoring و سیاست‌های امن production (secrets, headers, error handling) هم‌زمان با backend واقعی.

پس از انجام هر مورد، راهنمای حوزهٔ مسئول را با رفتار نهایی به‌روز کنید و این فهرست را اصلاح کنید. برنامه و وضعیت جاری را در سند یک قابلیت مخلوط نکنید.
