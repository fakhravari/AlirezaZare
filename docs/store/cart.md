# سبد، پیش‌فاکتور و سفارش

صفحه‌های سبد و Checkout به‌ترتیب در `Shop/Controllers/CartController.cs` و `CheckoutController.cs` رندر می‌شوند. رفتار سبد مرورگر در `Shop/wwwroot/shop/js/store/cart.js` و هماهنگی commerce در `js/store/commerce.js` است. این state مرورگر برای نمایش/تعامل است؛ قیمت نهایی، موجودی و سفارش باید با API سرور اعتبارسنجی شوند.

## مسیر جریان

کارت کالا → سبد مرورگر → ذخیرهٔ سبد حساب → خواندن سبد دیتابیس و join انتخاب‌ها → quote/اعتبارسنجی قیمت و موجودی → ساخت سفارش. `Account.CartItem` محصول، variant، طرح و تعداد را نگه می‌دارد. ویژگی‌های انتخاب‌شده در `Account.CartItemPurchaseOptionValue` با `IdCartItem` و `IdProductPurchaseOptionValue` ذخیره می‌شوند؛ متعلقات در `Account.CartItemAccessory` با `IdCartItem` و `IdProductAccessory`. مبلغ روی ردیف سبد cache نمی‌شود: قیمت محصول/طرح، گزینه‌ها و متعلقات از منابع قیمت جاری خوانده و به‌هم اضافه می‌شود؛ سرور سفارش را از سبد و همین ارتباط‌ها می‌سازد و snapshot قیمت و انتخاب‌ها را روی `OrderItem` ثبت می‌کند. مهاجرت ۰۶۸ انتخاب‌های JSON قدیمی را backfill می‌کند؛ ۰۶۹ ستون `Account.CartItem.OptionsJson` را حذف کرد؛ مهاجرت‌های ۰۷۰/۰۷۱ قیمت موقت سبد را افزودند و backfill کردند؛ ۰۷۲ آن cache را حذف می‌کند. snapshot مستقل سفارش در `OrderItem.OptionsJson` باقی می‌ماند. مرجع قیمت و optionها [طرح فروش](sales-plans.md) و مرجع ورود/نشانی [حساب](../account/profile.md) است.

کد تخفیف از `POST /api/account/coupon/quote` با سبد ذخیره‌شدهٔ حساب اعتبارسنجی و مبلغ واجد شرایط در سرور محاسبه می‌شود. checkout کد را دوباره با همان سبد و قیمت جاری اعتبارسنجی می‌کند؛ مبلغ تخفیف از جمع اقلام طرح عادیِ بدون تخفیف محاسبه و مصرف کوپن در `Store.CouponUsage` ثبت می‌شود. سفارش مبلغ ناخالص، مبلغ تخفیف و شناسهٔ کوپن را در `Store.Order` نگه می‌دارد. مقدار مرورگر فقط برای یادآوری کد واردشده است و مرجع مبلغ نیست. مهاجرت ۰۷۳ ستون‌های snapshot کوپن را به سفارش اضافه می‌کند.

دکمهٔ «ثبت نهایی و صدور فاکتور» در Checkout فقط سفارش/فاکتور را در دیتابیس ثبت می‌کند؛ پرداخت آنلاین هنوز فعال نیست. پس از موفقیت، سبد پاک می‌شود و شماره، جمع، تخفیف و مبلغ فاکتور در همان صفحه نمایش داده می‌شود. وضعیت سفارش `pending-payment` باقی می‌ماند تا اتصال درگاه در [راهنمای پرداخت](payment.md) پیاده شود؛ ثبت فاکتور به معنی دریافت وجه نیست.

صفحهٔ عمومی پیگیری سفارش از `POST /api/store/orders/tracking` استفاده می‌کند. درخواست باید کد سفارش و شمارهٔ همراه همان snapshot نشانی ارسال را داشته باشد؛ API فقط وضعیت سفارش، شرکت/کد حمل و تاریخچهٔ وضعیت/رهگیری را برمی‌گرداند و مبلغ، اقلام و نشانی را افشا نمی‌کند. درخواست‌ها بر اساس IP محدود می‌شوند و سفارش‌های نمایشی قابل استعلام نیستند.

## نکات تغییر

- کلید خط باید محصول، تنوع و طرح انتخابی را از هم جدا کند.
- محدودیت تعداد در مرورگر از کمینهٔ موجودی offer همان طرح و موجودی تنوع انتخاب‌شده گرفته می‌شود؛ این محدودیت راهنمای UI است. quote سبد، ذخیرهٔ سبد حساب و ثبت فاکتور هرکدام موجودی و فعال‌بودن طرح را از سرور دوباره کنترل می‌کنند.
- خطاهای افزودن، تغییر تعداد، quote پیش‌فاکتور و ثبت فاکتور با مرحله و علت قابل‌اقدام به کاربر نمایش داده می‌شوند؛ کدهای خام API فقط برای کنترل برنامه‌اند و متن نمایشی در owner همان صفحه نگهداری می‌شود.
- ثبت فاکتور در وضعیت `pending-payment` موجودی را رزرو یا از انبار کم نمی‌کند؛ تا زمان افزودن سازوکار رزرو/انقضای سفارش، دو فاکتور جداگانه می‌توانند برای آخرین موجودی صادر شوند.
- مبلغ سفارش در checkout از quote سرور و join انتخاب‌های شناسه‌محور محاسبه می‌شود؛ مبلغ ارسالی مرورگر معتبر نیست.
- state مهمان/کاربر و مهاجرت دادهٔ قدیمی را در `storage.js` و API بررسی کنید.
- order detail باید ارتباط نسخهٔ قیمت را حفظ کند تا مغایرت‌گیری ممکن باشد؛ قبل از تغییر schema، entity و migration را در [database](../architecture/database.md) دنبال کنید.

صفحهٔ سبد و checkout noindex هستند. بررسی: همگام‌سازی سبد حساب، ساخته‌شدن سفارش فقط از ردیف‌های دیتابیس، cart خالی/پر، خطای quote، تغییر قیمت و ارسال تکراری.
