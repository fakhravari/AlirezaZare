# آمادگی و مرزهای backend

این راهنما خلاصهٔ وضعیت جاری اتصال داده است. قرارداد تفصیلی هر حوزه در راهنمای همان حوزه نگهداری می‌شود؛ دادهٔ seed نمونه است و به‌تنهایی منبع عملیاتی نهایی کسب‌وکار محسوب نمی‌شود. در اختلاف مستندات، کد و runtime مرجع‌اند.

## اتصال‌های جاری

| حوزه | منبع runtime | مرجع قرارداد |
|---|---|---|
| کاتالوگ، دسته، برند و محتوای فروشگاه | repositoryهای SQL و API فروشگاه | [منابع داده](data-sources.md)، [کاتالوگ](../store/catalog.md) |
| سبد، نشانی، علاقه‌مندی، مقایسه، سفارش و پیگیری قیمت | API حساب و دیتابیس | [حساب](../account/profile.md)، [سبد و تسویه](../store/cart.md) |
| طرح فروش، quote و اعتبارسنجی checkout | API طرح فروش، Store و Warehouse | [فروش چندطرحی](../store/sales-plans.md) |
| دیدگاه و پرسش محصول | API بازخورد محصول و جدول `Store.ProductFeedback` | [محصول](../store/product.md)، [مدیریت](../admin/README.md) |
| محتوای مجله و مقاله | منبع دیتابیس و API تعامل حساب | [صفحه‌ها و محتوا](../content/pages.md) |
| پنل فروشگاه و انبار | APIهای مجزای Admin با مجوزهای مدیر | [راهنمای Admin](../admin/README.md) |

دادهٔ runtime در `localStorage` نگهداری نمی‌شود؛ کلیدهای قدیمی فقط برای انتقال یک‌باره خوانده و حذف می‌شوند. cache عمومی بین درخواست‌ها برای داده‌های کاربر یا کاتالوگ فرض نشود؛ جزئیات منبع و استثناهای runtime در [منابع داده](data-sources.md) آمده است.

## کارهای باز

- درگاه بانکی واقعی، callback تأییدشده و بازپرداخت هنوز متصل نیستند؛ وضعیت‌های پرداخت شبیه‌سازی‌شده جای تأیید بانک را نمی‌گیرند. مرجع: [پرداخت](../store/payment.md).
- ثبت سفارش اولیه متصل است، اما موجودی هنگام ثبت رزرو نمی‌شود. حوالهٔ انبار پس از تأیید پرداخت باید با عملیات مجاز پنل انجام شود؛ حوالهٔ تجمیعی تراکنشی در پنل وجود دارد.
- گردش کامل ساخت و مدیریت طرح‌های فروش و برخی عملیات نوشتن CMS هنوز کامل نیست. وضعیت دقیق هر بخش در راهنمای [طرح فروش](../store/sales-plans.md) و [مدیریت](../admin/README.md) نگهداری می‌شود.
- آزمون‌های تراکنشی روی پایگاه اصلی ممکن است identity، sequence، سابقهٔ ممیزی یا دادهٔ موقت باقی بگذارند؛ روش امن آزمون و محیط ایزوله در [کنترل کیفیت](../development/quality.md) تعریف شده است.

## قواعد طراحی قرارداد

- کلید رابطه‌ای پایدار باشد و به عنوان، ترجمه یا slug وابسته نشود.
- مبلغ هر API واحد روشن داشته باشد؛ مبلغ سرور از دادهٔ تأییدشده محاسبه شود و ورودی مرورگر تنها برای تشخیص تغییر قیمت به کار رود.
- endpoint خصوصی، مالکیت داده را از نشست سروری بگیرد؛ payload عمومی نباید سفارش، نشانی یا تاریخچهٔ خصوصی کاربر را منتشر کند.
- خطای منبع داده نباید بی‌صدا به دادهٔ دمو برگردد. دادهٔ seed و شبیه‌سازی باید با برچسب و مرز روشن از عملیات واقعی جدا بمانند.
