# آمادگی داده برای اتصال backend

این بازبینی مسیر Controller → مدل/منبع → Razor → JavaScript → storage را بررسی می‌کند. وضعیت زیر متعلق به ۳۰ اکتبر ۲۰۲۶ است؛ وجود دادهٔ نمایشی به معنی وجود API عملیاتی نیست.

## بازبینی مدل دادهٔ صفحه‌ها — ۳۰ اکتبر ۲۰۲۶

مسیرهای MVC از نظر محل آماده‌سازی داده مرور شدند. برای دادهٔ قابل‌تغییر، View باید یک مدل typed بگیرد و از Controller یا source بخواند؛ بخش‌هایی که به‌طور عمدی فقط browser state هستند نباید با ViewModel سروریِ ساختگی پوشانده شوند.

| خانوادهٔ صفحه | جریان فعلی | آمادگی برای جایگزینی منبع |
|---|---|---|
| خانه، جستجو، صفحهٔ محصول، برندها | کاتالوگ نسخه‌دار از `ICatalogSource`؛ دادهٔ کامل سمت مرورگر از `_CatalogData` و صفحهٔ محصول علاوه بر آن مدل SEO/شناسهٔ سروری دارد | جایگزینی کاتالوگ با adapter API در مرز موجود؛ `Home`/جستجو هنوز client-render می‌شوند و SSR صفحه‌بندی/facet ندارند |
| فهرست و دیتیل مجله | فهرست `PageModel<MagazineIndexViewModel>` از `IMagazineContentSource`؛ دیتیل از `PageModel<MagazineDetailsModel>` و `JournalArticles` | فهرست دارای adapter است؛ دیتیل و محتوای مقاله هنوز در مدل ثابت C# هستند و باید منبع CMS/API همان قرارداد را بسازد |
| FAQ و معرفی برند | `PageModel<IReadOnlyList<FaqEntry>>` و `PageModel<BrandProfileModel>` | ورودی View مدل تایپ‌شده است؛ FAQ ثابت C# و بخشی از متن برند ثابت/JSON است |
| پروفایل، سفارش و کوپن | `IAccountDataSource` در Controller و projectionهای `ProfilePageViewModel`/`ProfileOrdersViewModel` | View از source مستقل شده؛ adapter حساب دمو است و با endpoint سروری جایگزین می‌شود |
| آدرس، علاقه‌مندی، مقایسه، سبد و checkout | بیشتر state از `localStorage` و renderer مرورگر می‌آید؛ Razor فقط پوستهٔ اولیه می‌دهد | تا ساخت endpoint، مالک داده مرورگر است. ابتدا قرارداد async سمت کاربر و endpoint لازم است؛ صرف افزودن ViewModel سروری اتصال API ایجاد نمی‌کند |
| تماس و صفحه‌های خدمات/قوانین | متن تحریریه در View، ورودی فرم سمت مرورگر و metadata در `PageModel` | محتوای ثابت فعلی API ندارد؛ اگر CMS لازم شد، متن/بخش‌ها به مدل محتوای typed و source جدا منتقل شوند |

در این بررسی، منبع حساب از Razor به `ProfileController` منتقل شد و آرشیو مجله از anonymous objectهای داخل View به `MagazineIndexViewModel` و `IMagazineContentSource` رفت. کارت‌های آرشیو از همان `JournalArticles` دیتیل عنوان/خلاصه/تصویر می‌گیرند. تاریخ انتشار برای دادهٔ نمونه خالی می‌ماند چون تاریخ واقعی وجود ندارد؛ زمان مطالعه هم هنوز نمونه است. متن ثابت صفحات محتوا عمداً به مدل‌های نمایشی ساختگی منتقل نشد، چون منبع CMS/API در runtime ندارند.

## نتیجهٔ بررسی و تغییر اجرایی

کاتالوگ مشترک ساختاریافته است، اما کل پروژه هنوز به backend متصل نیست. مرز قابل‌جایگزینی خواندن کاتالوگ [ICatalogSource](../../Shop/Services/ICatalogSource.cs) است. محصول، برند، sitemap و bootstrap مرورگر از قرارداد async همراه CancellationToken استفاده می‌کنند. پیاده‌سازی فایل همچنان cache همگام دارد؛ adapter شبکه باید داده را با همان CatalogSnapshot.Parse اعتبارسنجی کند و نباید با خطای API بی‌صدا به دادهٔ دمو برگردد.

سفارش و کوپن از Razor و JavaScript خارج و در [account-demo.json](../../Shop/App_Data/account-demo.json) یکپارچه شده‌اند. [AccountData](../../Shop/Models/AccountData.cs) رابطه‌ها و مبالغ را اعتبارسنجی می‌کند. [IAccountDataSource و ICommerceOfferSource](../../Shop/Services/IAccountDataSource.cs) دو مرز مستقل حساب و پیشنهاد عمومی هستند؛ پیاده‌سازی demo یک snapshot به‌ازای درخواست دارد. فایل خارج از wwwroot است و در publish کپی می‌شود. bootstrap عمومی فقط کد و درصد تخفیف را می‌دهد؛ سابقهٔ سفارش فقط در پروفایل serialize می‌شود. احراز هویت واقعی هنوز پیاده نشده است.

ثبت‌نام اکنون کد ایمیل را از [EmailVerificationController](../../Shop/Controllers/EmailVerificationController.cs) می‌گیرد؛ [SmtpEmailSender](../../Shop/Services/SmtpEmailSender.cs) با تنظیمات `Email:Smtp` ایمیل می‌فرستد و [EmailVerificationCodeStore](../../Shop/Services/EmailVerificationCodeStore.cs) کد hash‌شدهٔ یک‌بارمصرف را با انقضای ۱۰ دقیقه، حداکثر پنج تلاش و فاصلهٔ ارسال مجدد ۶۰ ثانیه نگه می‌دارد. endpoint ارسال به سقف پنج درخواست در هر IP طی پنج دقیقه محدود است. TLS برای SMTP فعال است و مقدار password در `appsettings.json` خالی است؛ برای توسعه از `dotnet user-secrets set "Email:Smtp:Password" "<new SMTP secret>" --project Shop/Shop.csproj` و در استقرار از متغیر محیطی `Email__Smtp__Password` استفاده کنید. `npm run check` اکنون فایل‌های `appsettings*.json` tracked را برای secretهای غیرخالی کنترل می‌کند؛ این guard جلوی افزودن accidental credential در تغییرات بعدی را می‌گیرد، اما Git history را اسکن یا پاک نمی‌کند. اتصال دیتابیس و FTP در کد فعلی مصرف‌کننده ندارند و پیکربندی شامل دسترسی آن‌ها از فایل tracked حذف شده است. ممیزی محلی تاریخچهٔ موجود Git، بدون چاپ مقادیر، credentialهای پیکربندی را در ۵ نسخه از ۷ نسخهٔ JSON قابل‌خواندن `appsettings.json` پیدا کرد (۸ revision فایل بررسی شد؛ یکی JSON قابل‌خواندن نبود). وجود ۳ remote-tracking ref محلی نیز انتشار یا دسترس‌پذیری remote را به‌تنهایی ثابت نمی‌کند. دارندهٔ دسترسی باید credentialهای SMTP/DB/FTP سابق را نزد ارائه‌دهندگان بچرخاند؛ اگر commitهای درگیر به remote رسیده‌اند، پاک‌سازی تاریخچه باید با هماهنگی cloneها و مصرف‌کنندگان انجام شود. این اقدام از محیط ارائه‌دهنده و دارندهٔ دسترسی لازم است و از این مخزن انجام نشده است. این تغییر فقط تأیید ایمیل را سروری کرده است؛ ساخت حساب پایدار، ورود با گذرواژه و session هنوز دمو هستند. store کدها در حافظهٔ یک process است و برای چند replica باید به cache مشترک منتقل شود.

## قرارداد تبدیل داده

- id رابطه‌ای مستقل از عنوان و ترجمه بماند. slug فقط مسیر خوانا است؛ تغییر عنوان نباید رابطه‌ها را تغییر دهد.
- تاریخ انتقال ISO باشد؛ تاریخ شمسی و ارقام فارسی در نمایش ساخته شوند. رخدادهای واقعی UTC با offset و تاریخ بدون ساعت DateOnly باشند. انقضای کوپن دمو با تاریخ UTC جاری و شامل روز انقضا محاسبه می‌شود؛ منطقهٔ زمانی تجاری در API باید صریح تعیین شود.
- مبالغ حساب عدد صحیح تومان با currency برابر IRT هستند. کاتالوگ فعلی قیمت را در مقیاس میلیون تومان نگه می‌دارد و renderer آن را تبدیل می‌کند؛ adapter باید دقیقاً یک‌بار تبدیل کند. ریال درگاه با تومان UI یکسان نیست؛ واحد هر پاسخ الزامی است.
- enumهای انتقال انگلیسی باشند؛ برچسب فارسی، رنگ و کلاس CSS متعلق به لایهٔ نمایش‌اند.
- schemaVersion در دادهٔ کاتالوگ و حساب مستقل است. تغییر schema باید migration و اعتبارسنجی هم‌زمان مصرف‌کننده داشته باشد. cache یا storage نسخهٔ آینده بازنویسی نشود.
- مدل فهرست API پیشنهادی شامل items، page، pageSize و totalCount است؛ خطای قابل نمایش شامل code، message، fieldErrors و traceId باشد. این envelope هنوز endpoint پیاده‌شده نیست.
- API خصوصی باید scope کاربر را سروری اعمال کند؛ فایل دمو را با اطلاعات مشتری واقعی پر نکنید. bootstrap عمومی نباید شامل سفارش، آدرس یا سابقهٔ مصرف خصوصی شود.

## مسیر جایگزینی

۱. ابتدا قرارداد backend را به مدل‌های کاتالوگ و حساب نگاشت و adapterها را در Program.cs جایگزین کنید. اعتبارسنجی و serialization امن را حفظ کنید. پیاده‌سازی demo و واقعی باید انتخاب صریح داشته باشند.

۲. عملیات نوشتن (سبد، آدرس، پیگیری، علاقه‌مندی و سفارش) به سرویس async نیاز دارند؛ wrapper storage فعلی، API نوشتن نیست. UI باید loading، خطای شبکه، لغو، پاسخ دیرهنگام و تداخل نسخه را مدیریت کند. اعلان موفقیت فقط پس از پاسخ موفق ارسال شود.

۳. سفارش کامل را با ردیف و snapshot قیمت/آدرس بسازید. مبلغ ارسالی مرورگر، کوپن محلی یا وضعیت پرداخت UI مبنای قطعی سفارش نباشد. callback پرداخت و ثبت سفارش تکراری باید در backend کنترل شوند.

۴. پس از جایگزینی هر حوزه، دمو همان حوزه را از مسیر runtime خارج کنید و تست قرارداد، خطا، دسترسی و دادهٔ خالی اجرا کنید. endpoint تأیید ایمیل ساخته شده، اما ساخت/ورود حساب و دیتابیس هویت هنوز عملیاتی نیستند.

## بررسی تغییر فعلی

# Sales-plan API adapter

برای قابلیت طرح‌های فروش، `ISalesPlanSource` مرز منبع داده و `DemoSalesPlanSource` adapter فقط‌خواندنی fixture است. APIهای quote و validate-cart در `SalesPlansController` قیمت، انتخاب ویژگی و متعلقات را از دادهٔ سرور بازسازی می‌کنند. پیاده‌سازی به دیتابیس، کنترل تراکنشی موجودی پس از پرداخت و ثبت سفارش وصل نیست؛ وضعیت جزئی و کارهای باقی‌مانده در [راهنمای طرح‌های فروش](../store/sales-plans.md) ثبت شده است.

## نیازمندی‌های سیستم انبار و اتصال به فروشگاه — ۷ نوامبر ۲۰۲۶

این بخش مرجع نیازمندی‌های تأییدشدهٔ سیستم انبار و مرز آن با فروشگاه است. migration اولیهٔ SQL Server در [001-initial-schema.sql](../../Shop/Features/Warehouse/Database/Migrations/001-initial-schema.sql) پیاده شده و روی دیتابیس پیکربندی‌شده اعمال شده است؛ اتصال runtime برنامه، API و رابط انبار هنوز پیاده‌سازی نشده‌اند.

### نیازمندی‌های تأییدشده

- تمام عملیات رابط کاربری انبار باید به‌صورت ناهمگام (AJAX) انجام شوند و باعث بارگذاری مجدد یا پیمایش کامل صفحه نشوند.
- ساختار پوشه‌ها و namespaceهای پیاده‌سازی انبار باید بر اساس قابلیت‌ها و مسئولیت‌های همان قابلیت سازمان‌دهی شود؛ ViewModel اختصاصی هر قابلیت در همان بخش نگهداری شود و فقط مدل‌های واقعاً مشترک در بخش مشترک قرار بگیرند. این دسته‌بندی باید با قرارداد پوشه‌های MVC پروژه در [نمای کلی معماری](overview.md) سازگار باشد.
- جدول‌های پایگاه‌داده باید بر اساس دامنهٔ مالکیت و مصرف در schemaهای جدا و متناسب گروه‌بندی شوند؛ جدول‌های متعلق به انبار در schema دامنهٔ انبار قرار می‌گیرند و با جدول‌های دامنه‌های دیگر در schema عمومی مخلوط نمی‌شوند. نام‌گذاری و مرز دقیق schemaها در طراحی فنی تعیین می‌شود.
- هر جدول کلید اصلی با نام `Id` دارد. نام کلید خارجی از الگوی `Id<Entity>` پیروی می‌کند؛ برای نمونه، ارجاع به جدول `Book` با ستون `IdBook` مشخص می‌شود. ستون کلید اصلی و سپس کلیدهای خارجی در ابتدای تعریف ستون‌های جدول می‌آیند و بعد از آن‌ها ستون‌های دیگر قرار می‌گیرند. نام جدول‌ها و ستون‌ها باید روشن، یکدست و معنادار باشد.
- شرکت‌ها و انبارهای متعلق به آن‌ها باید قابل تعریف باشند؛ هر شرکت دقیقاً یک انبار فروش دارد. کاربر پنل با دسترسی کامل می‌تواند شرکت متصل به سایت را تغییر دهد و تغییر فوراً اعمال می‌شود. موجودی هر انبار مستقل و در سطح خود انبار نگهداری می‌شود و موقعیت داخلی مانند سالن/قفسه در دامنهٔ فعلی نیست. شرکت پیش‌فرض برای فروش سایت، شرکتی است که انبار فروش متصل به سایت را در اختیار دارد.
- در پنل مفهوم «شرکت فعال» یا انتخاب دستی شرکت وجود ندارد؛ هر کاربر بر اساس مجوزهایش شرکت‌ها و گردش‌های مجاز را می‌بیند. تعیین دسترسی افراد به انبار و شرکت‌های مجاز از بخش «مدیریت افراد» انجام می‌شود. این دسترسی‌ها مستقل از تنظیم شرکت متصل به فروش سایت هستند.
- موجودی فروش سایت از انبار فروشِ یک شرکت تأمین می‌شود؛ موجودی شرکت‌های دیگر با آن تجمیع نمی‌شود.
- برای هر انبار فروش، انتخاب یک طرح فروش از طرح‌های فروشگاه به‌عنوان طرح مالک اجباری است؛ اتصال انبار فروش بدون انتخاب طرح مالک کامل نیست. موجودی سایت برای هر ترکیب تنوع و طرح فروش از همان انبار فروش جداگانه خوانده می‌شود.
- سطح موجودی باید هم کالای بدون تنوع و هم کالای دارای تنوع را پشتیبانی کند؛ تنوع‌ها در خود انبار تعریف و مدیریت می‌شوند. موجودی به تفکیک انبار، تنوع کالا و طرح فروش نگهداری می‌شود و موجودی طرح‌ها با هم ادغام نمی‌شود. در هر سند انبار یک طرح فروش انتخاب می‌شود و همان طرح برای همهٔ ردیف‌های آن سند اعمال می‌شود.
- هر کالا یک واحد اصلی دارد؛ موجودی و فروش بر مبنای واحد اصلی ثبت می‌شوند. کالا می‌تواند واحدهای دیگری با ضریب تبدیل به واحد اصلی داشته باشد. در سند انبار کاربر واحد و مقدار را انتخاب/وارد می‌کند؛ سیستم مقدار واردشده در واحد انتخابی را با ضریب همان واحد به واحد اصلی تبدیل می‌کند. مقدار انتخابی و ضریب تبدیل در سند نگهداری می‌شوند و اثر موجودی بر اساس مقدار نرمال‌شده به واحد اصلی محاسبه می‌شود. تنوع می‌تواند واحد نمایشی داشته باشد، اما واحد موجودی مستقل ندارد و مقدار آن همواره به واحد اصلی کالا تبدیل می‌شود. مقدار فروش و مقدار ذخیره‌شده حداکثر سه رقم اعشار دارند؛ رقم‌های بیشتر بریده می‌شوند، نه گرد. ردیابی واحدبه‌واحد با شمارهٔ سریال لازم نیست.
- هنگام ایجاد سفارش موجودی رزرو نمی‌شود. پس از پرداخت، سفارش‌ها بر اساس زمان پرداخت از قدیمی به جدید در بخش انبار پردازش می‌شوند؛ کنترل موجودی، تأیید انبار و ایجاد حوالهٔ خروج قطعی برای هر سفارش در یک تراکنش واحد انجام می‌شود. حواله از انبار فروشِ شرکت متصل به سایت صادر می‌شود، به مرجع مشتریِ سفارش متصل است، شمارهٔ سفارش را نگه می‌دارد و تاریخ سند آن روز تأیید انبار/ایجاد حواله است. اگر هر قلم سفارش موجودی کافی نداشته باشد، وضعیت سفارش تغییر نمی‌کند و در همان وضعیت تا بررسی ادمین می‌ماند. اگر API برگشت وجه خطا دهد یا پاسخ ندهد، retry خودکار لازم نیست و به کاربر گفته می‌شود برای پیگیری با مدیریت تماس بگیرد.
- snapshot موجودی سایت با هر تغییر روی سند انبار به‌روزرسانی می‌شود؛ سندهای بدون تیک اثر بر موجودی در گردش ثبت می‌شوند اما مقدار موجودی را تغییر نمی‌دهند.
- اگر موجودی کافی نباشد، خرید ممکن نیست و باید پیام کمبود موجودی نشان داده شود؛ پیش‌فروش در دامنهٔ فعلی نیست.
- اگر سرویس انبار موقتاً در دسترس نباشد، فروشگاه از آخرین موجودی دریافت‌شده استفاده می‌کند. اگر هنوز هیچ snapshot موجودی دریافت نشده باشد، کالا می‌تواند نمایش داده شود اما برای خرید موجود نیست و موجودی قابل‌فروش صفر در نظر گرفته می‌شود.
- رزرو مدت‌دار موجودی نداریم.
- حداقل موجودی فقط برای طرح عادی، به‌ازای هر کالا یا تنوع و در هر انبار جداگانه قابل تنظیم است؛ از موجودی قابل‌فروش طرح عادی سایت کسر می‌شود و برای طرح‌های دیگر حداقل موجودی جدا نداریم. اگر مقدار حداقل بیشتر از صفر باشد، هنگام رسیدن موجودی طرح عادی در آن انبار به حد یا کمتر، در پنل انبار هشدار نمایش داده می‌شود. ماندهٔ فیزیکی انبار منفی نمی‌شود و سند خروج بیشتر از موجودی فیزیکی رد می‌شود.
- تمام گردش‌های ورود، خروج، انتقال و اصلاح موجودی زمان ثبت خودکار و کاربر ثبت‌کننده را نگه می‌دارند؛ علاوه بر آن، تاریخ سند/گردش برای انتخاب کاربر قابل تنظیم است. ثبت دلیل اختیاری است.
- تاریخ سند را کاربر از گذشته تا امروز انتخاب می‌کند و تاریخ آینده مجاز نیست؛ زمان واقعی ثبت به‌صورت خودکار و جدا نگهداری می‌شود.
- شمارهٔ هر سند انبار به‌صورت خودکار، ترتیبی و یکتا تولید می‌شود؛ شمارهٔ تکراری مجاز نیست و شمارهٔ سند حذف‌شده دوباره استفاده نمی‌شود، پس امکان فاصله در توالی وجود دارد.
- مقدار ردیف‌های سند انبار منفی نیست؛ جهت افزایش یا کاهش را نوع سند و وضعیت آن تعیین می‌کند.
- نوع سندهای انبار باید قابل مدیریت باشد و در تعریف هر نوع یک تیک «تأثیر بر موجودی» وجود داشته باشد. اگر تیک فعال باشد، جهت تغییر را نوع سند رسید یا حواله و وضعیت موقت/قطعی آن تعیین می‌کند؛ اگر غیرفعال باشد، سند در گردش و سابقه ثبت می‌شود اما موجودی را تغییر نمی‌دهد.
- نوع سندی که در گردش‌ها استفاده شده حذف نمی‌شود و فقط غیرفعال می‌شود؛ گردش‌های قبلی با همان نوع برای مشاهده حفظ می‌شوند.
- شرکت یا انباری که گردش ثبت‌شده دارد حذف نمی‌شود و فقط غیرفعال می‌شود؛ سوابق و گردش‌های قبلی آن حفظ می‌شوند.
- هر سند باید مرجع/طرف مرتبط داشته باشد و انتخاب مرجع اجباری است. فهرست مرجع‌ها در پنل انبار مدیریت می‌شود و می‌تواند شخص، سازمان یا هر نوع طرف دیگری باشد؛ اگر مرجع یک انبار متعلق به شرکت‌های خودمان باشد، به شناسهٔ همان انبار پیوند می‌خورد. گردش‌های جابه‌جایی نیز جداگانه ثبت می‌شوند: خروج از انبار مبدأ و ورود به انبار مقصد دو گردش مستقل‌اند، هرکدام مرجع همان انبار را می‌گیرند و شناسهٔ انتقال مشترکی میانشان لازم نیست. شکل فنی مدل مرجع هنوز تعیین نشده است.
- مرجعی که در سندهای انبار استفاده شده حذف نمی‌شود و فقط غیرفعال می‌شود؛ اسناد قبلی مرجع خود را برای مشاهده حفظ می‌کنند.
- هر سند دو وضعیت موقت و قطعی دارد، در هر دو وضعیت قابل ویرایش و حذف است و می‌تواند از قطعی به موقت برگردد. اگر نوع سند بر موجودی اثرگذار باشد، جهت اثر موقت و قطعی چنین است: رسید موقت موجودی را کم و رسید قطعی زیاد می‌کند؛ حواله موقت موجودی را زیاد و حواله قطعی کم می‌کند. سندی که گزینهٔ اثر بر موجودی آن خاموش است، در هر دو وضعیت فقط در گردش ثبت می‌شود و موجودی را تغییر نمی‌دهد. تغییر وضعیت، ویرایش یا حذف باید موجودی را بر اساس اثر جدید دوباره محاسبه کند، بدون دوباره‌شماری.
- نگهداری نسخه‌های قبلی سند پس از ویرایش یا حذف لازم نیست؛ تاریخ و کاربرِ گردش ثبت می‌شوند و دلیل در صورت ورود نگهداری می‌شود.
- انبارگردانی دستی با یک سند عادی انبار ثبت می‌شود و جریان یا رفتار محاسباتی ویژه‌ای ندارد؛ اثر آن تابع نوع سند و وضعیت موقت/قطعی است.
- انتخاب کالا و تنوع در اسناد و انبارگردانی دستی است؛ پشتیبانی از بارکدخوان لازم نیست.
- مرجوعی به‌صورت دستی و با یک نوع سند عادی انبار ثبت می‌شود؛ جریان یا سناریوی اختصاصی جداگانه لازم نیست. سند می‌تواند نام مشتری و سفارش مرتبط را داشته باشد و اثر آن بر موجودی طبق گزینهٔ مؤثر/غیرمؤثر همان نوع سند تعیین می‌شود.
- دسترسی‌ها باید با ساختار درختیِ مجوزها تعریف شوند تا بعداً نقش‌ها و سطح دسترسی هر عملیات قابل گسترش باشد و از بخش «مدیریت افراد» به کاربران تخصیص یابند. نسخهٔ اولیه فقط یک کاربر/نقش دارد و همان دسترسی کامل به همهٔ عملیات انبار را دریافت می‌کند.
- مدیریت انبار و مدیریت فروشگاه بخشی از یک سامانهٔ مدیریتی واحد هستند؛ در رابط کاربری به‌صورت حوزه‌ها و منوهای جدا از هم ارائه می‌شوند، نه به‌عنوان دو سامانهٔ مستقل.
- انبار برای هر کالا به شناسهٔ محصول مرجع ارجاع می‌دهد و مالک تعریف تنوع‌هاست؛ همان تنوع‌ها با شناسهٔ مشترک در فروشگاه به‌عنوان گزینه‌های قابل خرید مصرف می‌شوند و موجودی انبار با همان شناسهٔ تنوع ثبت می‌شود. کد کالای جداگانه برای تنوع لازم نیست؛ شناسهٔ سیستمی کافی است. قیمت و اطلاعات نمایشی فروش همچنان متعلق به فروشگاه است.
- غیرفعال‌شدن یا حذف تنوع از انتخاب‌های فعال فروش نباید سابقهٔ گردش و موجودی انبار آن را پاک کند؛ اطلاعات تنوع باید برای مشاهدهٔ سابقه و پیگیری انبار حفظ شود.
- انبار از شناسهٔ محصول مرجع استفاده می‌کند و تنوع‌ها را تعریف می‌کند؛ همان شناسه‌های تنوع مرجع مشترک گزینه‌های قابل خرید فروشگاه‌اند. ردیابی سری ساخت/بچ، تاریخ انقضا و شمارهٔ سریال لازم نیست.
- قیمت‌گذاری کاملاً بیرون از دامنهٔ انبار است و در مدیریت فروشگاه انجام می‌شود. سند انبار نباید قیمت فروش، تخفیف یا محاسبهٔ مبلغ کالا را مالک شود؛ در اتصال بعدی، اگر گردش مالی سند لازم شد، واحد و مرجع مبلغ باید جداگانه تعریف شود.

### نکته‌های باقی‌مانده برای طراحی فنی

- سیاست دقیق محاسبه/به‌روزرسانی موجودی هنگام تغییر سند موقت/قطعی، ویرایش یا حذف باید در پیاده‌سازی تراکنشی اعمال و آزمون شود.
- ساختار مدل فنی مرجع مشترک، شناسه‌های پایدار محصول/تنوع و قرارداد API هنوز طراحی نشده‌اند.
- دادهٔ فعلی فروشگاه نمونه است: کاتالوگ ۳۰ کالا دارد (۷ کالای تنوع‌دار)؛ تنوع‌ها به شکل گزینه‌ها و کلیدهای ترکیبی متنی ثبت شده‌اند و شناسهٔ مستقل ندارند. همچنین فیلد واحد کالا در کاتالوگ نیست. در اتصال انبار باید برای تنوع‌ها شناسهٔ پایدار ایجاد/نگاشت شود و واحد اصلی و ضرایب تبدیل به مدل محصول افزوده شوند.
- `stockQuantity` در offerهای `sales-plans-demo.json` دادهٔ موجودی نمونه است؛ پس از اتصال، مرجع موجودی واقعی باید موجودی انبار به تفکیک طرح باشد و مقدارهای fixture نباید منبع حقیقت بمانند.

### مرز مسئولیت پیشنهادی برای ادامهٔ طراحی

| انبار | فروشگاه / مدیریت فروش |
|---|---|
| شرکت، انبار و تنظیم اتصال انبار فروش | قیمت پایه، قیمت طرح و تخفیف |
| رسید، حواله و اقلام هر سند | نام/شرح و محتوای بازاریابی محصول |
| ارجاع به محصول/ویژگی مرجع مشترک و نگهداری موجودی هر شناسه | نمایش کاتالوگ و انتخاب خرید |
| موجودی فیزیکی و گردش افزایشی/کاهشی | تصمیم قیمت نهایی و پیش‌فاکتور |
| ارائهٔ موجودی انبار و اجرای کنترل نهایی پس از پرداخت، با کسر حداقل موجودی سایت | قیمت پایه، قیمت طرح، تخفیف و تغییر وضعیت سفارش |

این جدول مرزبندی مفهومی است، نه قرارداد پیاده‌سازی API. برای جلوگیری از وابستگی متقابل، اتصال آینده باید از شناسه‌های پایدار محصول/تنوع و قرارداد صریح موجودی استفاده کند؛ انبار نباید مدل قیمت فروشگاه را بخواند.

### تصمیم‌های باز برای جلسهٔ طراحی

1. سندها: قواعد محاسبهٔ اتمیک موجودی هنگام تبدیل موقت/قطعی، بازگردانی وضعیت، ویرایش و حذف باید پیاده و آزمون شوند؛ نسخهٔ قبلی سند نگهداری نمی‌شود.
2. اتصال برنامه: تنظیم provider و دسترسی runtime، API و رابط انبار هنوز پیاده‌سازی نشده‌اند. تطبیق شناسه‌های محصول/تنوع با منبع فروشگاه و قرارداد خواندن/به‌روزرسانی snapshot موجودی نیز پیش از اتصال باید نهایی شود.

این موارد نیازمندی‌های تأییدشده، migration اولیه و کارهای باقیمانده را ثبت می‌کنند؛ migration فقط ساختار داده و رویهٔ تراکنشی پایه را فراهم می‌کند و به‌تنهایی اتصال عملیاتی برنامه را کامل نمی‌کند.
