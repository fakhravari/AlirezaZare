# آمادگی داده برای اتصال backend

این بازبینی مسیر Controller → مدل/منبع → Razor → JavaScript → storage را بررسی می‌کند. وضعیت زیر متعلق به ۳۰ اکتبر ۲۰۲۶ است؛ وجود دادهٔ نمایشی به معنی وجود API عملیاتی نیست.

## بازبینی مدل دادهٔ صفحه‌ها — ۳۰ اکتبر ۲۰۲۶

مسیرهای MVC از نظر محل آماده‌سازی داده مرور شدند. برای دادهٔ قابل‌تغییر، View باید یک مدل typed بگیرد و از Controller یا source بخواند؛ بخش‌هایی که به‌طور عمدی فقط browser state هستند نباید با ViewModel سروریِ ساختگی پوشانده شوند.

| خانوادهٔ صفحه | جریان فعلی | آمادگی برای جایگزینی منبع |
|---|---|---|
| خانه، جستجو، صفحهٔ محصول، برندها | کاتالوگ نسخه‌دار از `ICatalogSource`؛ دادهٔ کامل سمت مرورگر از `_CatalogData` و صفحهٔ محصول علاوه بر آن مدل SEO/شناسهٔ سروری دارد | جایگزینی کاتالوگ با adapter API در مرز موجود؛ `Home`/جستجو هنوز client-render می‌شوند و SSR صفحه‌بندی/facet ندارند |
| فهرست و دیتیل مجله | فهرست `PageModel<MagazineIndexViewModel>` از `IMagazineContentSource`؛ دیتیل از `PageModel<MagazineDetailsModel>` و `JournalArticles` | فهرست دارای adapter است؛ دیتیل و محتوای مقاله هنوز در مدل ثابت C# هستند و باید منبع CMS/API همان قرارداد را بسازد |
| FAQ و معرفی برند | `PageModel<IReadOnlyList<FaqEntry>>` و `PageModel<BrandProfileModel>` | ورودی View مدل تایپ‌شده است؛ FAQ ثابت C# و بخشی از متن برند ثابت/JSON است |
| پروفایل، سفارش و کوپن | `IAccountDataSource` در Controller و projectionهای `ProfilePageViewModel`/`ProfileOrdersViewModel` | View از source مستقل شده؛ adapter حساب دمو است و با endpoint سروری جایگزین می‌شود |
| آدرس، علاقه‌مندی، مقایسه، سبد و checkout | بیشتر state از `localStorage` و renderer مرورگر می‌آید؛ Razor فقط پوستهٔ اولیه می‌دهد | تا ساخت endpoint، مالک داده مرورگر است. ابتدا قرارداد async سمت کاربر و endpoint لازم است؛ صرف افزودن ViewModel سروری اتصال API ایجاد نمی‌کند |
| تماس و صفحه‌های خدمات/قوانین | متن تحریریه در View، ورودی فرم سمت مرورگر و metadata در `PageModel` | محتوای ثابت فعلی API ندارد؛ اگر CMS لازم شد، متن/بخش‌ها به مدل محتوای typed و source جدا منتقل شوند |

در این بررسی، منبع حساب از Razor به `ProfileController` منتقل شد و آرشیو مجله از anonymous objectهای داخل View به `MagazineIndexViewModel` و `IMagazineContentSource` رفت. کارت‌های آرشیو از همان `JournalArticles` دیتیل عنوان/خلاصه/تصویر می‌گیرند. تاریخ انتشار برای دادهٔ نمونه خالی می‌ماند چون تاریخ واقعی وجود ندارد؛ زمان مطالعه هم هنوز نمونه است. متن ثابت صفحات محتوا عمداً به مدل‌های نمایشی ساختگی منتقل نشد، چون منبع CMS/API در runtime ندارند.

## نتیجهٔ بررسی و تغییر اجرایی

کاتالوگ مشترک ساختاریافته است، اما کل پروژه هنوز به backend متصل نیست. مرز قابل‌جایگزینی خواندن کاتالوگ [ICatalogSource](../../Shop/Services/ICatalogSource.cs) است. محصول، برند، sitemap و bootstrap مرورگر از قرارداد async همراه CancellationToken استفاده می‌کنند. پیاده‌سازی فایل همچنان cache همگام دارد؛ adapter شبکه باید داده را با همان CatalogSnapshot.Parse اعتبارسنجی کند و نباید با خطای API بی‌صدا به دادهٔ دمو برگردد.

سفارش و کوپن از Razor و JavaScript خارج و در [account-demo.json](../../Shop/App_Data/account-demo.json) یکپارچه شده‌اند. [AccountData](../../Shop/Models/AccountData.cs) رابطه‌ها و مبالغ را اعتبارسنجی می‌کند. [IAccountDataSource و ICommerceOfferSource](../../Shop/Services/IAccountDataSource.cs) دو مرز مستقل حساب و پیشنهاد عمومی هستند؛ پیاده‌سازی demo یک snapshot به‌ازای درخواست دارد. فایل خارج از wwwroot است و در publish کپی می‌شود. bootstrap عمومی فقط کد و درصد تخفیف را می‌دهد؛ سابقهٔ سفارش فقط در پروفایل serialize می‌شود. احراز هویت واقعی هنوز پیاده نشده است.

ثبت‌نام اکنون کد ایمیل را از [EmailVerificationController](../../Shop/Controllers/EmailVerificationController.cs) می‌گیرد؛ [SmtpEmailSender](../../Shop/Services/SmtpEmailSender.cs) با تنظیمات `Email:Smtp` ایمیل می‌فرستد و [EmailVerificationCodeStore](../../Shop/Services/EmailVerificationCodeStore.cs) کد hash‌شدهٔ یک‌بارمصرف را با انقضای ۱۰ دقیقه، حداکثر پنج تلاش و فاصلهٔ ارسال مجدد ۶۰ ثانیه نگه می‌دارد. endpoint ارسال به سقف پنج درخواست در هر IP طی پنج دقیقه محدود است. TLS برای SMTP فعال است و مقدار password در `appsettings.json` خالی است؛ برای توسعه از `dotnet user-secrets set "Email:Smtp:Password" "<new SMTP secret>" --project Shop/Shop.csproj` و در استقرار از متغیر محیطی `Email__Smtp__Password` استفاده کنید. `npm run check` اکنون فایل‌های `appsettings*.json` tracked را برای secretهای غیرخالی کنترل می‌کند؛ این guard جلوی افزودن accidental credential در تغییرات بعدی را می‌گیرد، اما Git history را اسکن یا پاک نمی‌کند. اتصال دیتابیس و FTP در کد فعلی مصرف‌کننده ندارند و پیکربندی شامل دسترسی آن‌ها از فایل tracked حذف شده است. ممیزی محلی تاریخچهٔ موجود Git، بدون چاپ مقادیر، credentialهای پیکربندی را در ۵ نسخه از ۷ نسخهٔ JSON قابل‌خواندن `appsettings.json` پیدا کرد (۸ revision فایل بررسی شد؛ یکی JSON قابل‌خواندن نبود). وجود ۳ remote-tracking ref محلی نیز انتشار یا دسترس‌پذیری remote را به‌تنهایی ثابت نمی‌کند. دارندهٔ دسترسی باید credentialهای SMTP/DB/FTP سابق را نزد ارائه‌دهندگان بچرخاند؛ اگر commitهای درگیر به remote رسیده‌اند، پاک‌سازی تاریخچه باید با هماهنگی cloneها و مصرف‌کنندگان انجام شود. این اقدام از محیط ارائه‌دهنده و دارندهٔ دسترسی لازم است و از این مخزن انجام نشده است. این تغییر فقط تأیید ایمیل را سروری کرده است؛ ساخت حساب پایدار، ورود با گذرواژه و session هنوز دمو هستند. store کدها در حافظهٔ یک process است و برای چند replica باید به cache مشترک منتقل شود.

## قرارداد تبدیل داده

- id رابطه‌ای مستقل از عنوان و ترجمه بماند. slug فقط مسیر خوانا است؛ تغییر عنوان نباید رابطه‌ها را تغییر دهد.
- تاریخ انتقال ISO باشد؛ تاریخ شمسی و ارقام فارسی در نمایش ساخته شوند. رخدادهای واقعی UTC با offset و تاریخ بدون ساعت DateOnly باشند. انقضای کوپن دمو با تاریخ UTC جاری و شامل روز انقضا محاسبه می‌شود؛ منطقهٔ زمانی تجاری در API باید صریح تعیین شود.
- مبالغ حساب عدد صحیح تومان با currency برابر IRT هستند. کاتالوگ فعلی قیمت را در مقیاس میلیون تومان نگه می‌دارد و renderer آن را تبدیل می‌کند؛ adapter باید دقیقاً یک‌بار تبدیل کند. ریال درگاه با تومان UI یکسان نیست؛ واحد هر پاسخ الزامی است.
- enumهای انتقال انگلیسی باشند؛ برچسب فارسی، رنگ و کلاس CSS متعلق به لایهٔ نمایش‌اند.
- schemaVersion در دادهٔ کاتالوگ و حساب مستقل است. تغییر schema باید migration و اعتبارسنجی هم‌زمان مصرف‌کننده داشته باشد. cache یا storage نسخهٔ آینده بازنویسی نشود.
- مدل فهرست API پیشنهادی شامل items، page، pageSize و totalCount است؛ خطای قابل نمایش شامل code، message، fieldErrors و traceId باشد. این envelope هنوز endpoint پیاده‌شده نیست.
- API خصوصی باید scope کاربر را سروری اعمال کند؛ فایل دمو را با اطلاعات مشتری واقعی پر نکنید. bootstrap عمومی نباید شامل سفارش، آدرس یا سابقهٔ مصرف خصوصی شود.

## مسیر جایگزینی

۱. ابتدا قرارداد backend را به مدل‌های کاتالوگ و حساب نگاشت و adapterها را در Program.cs جایگزین کنید. اعتبارسنجی و serialization امن را حفظ کنید. پیاده‌سازی demo و واقعی باید انتخاب صریح داشته باشند.

۲. عملیات نوشتن (سبد، آدرس، پیگیری، علاقه‌مندی و سفارش) به سرویس async نیاز دارند؛ wrapper storage فعلی، API نوشتن نیست. UI باید loading، خطای شبکه، لغو، پاسخ دیرهنگام و تداخل نسخه را مدیریت کند. اعلان موفقیت فقط پس از پاسخ موفق ارسال شود.

۳. سفارش کامل را با ردیف و snapshot قیمت/آدرس بسازید. مبلغ ارسالی مرورگر، کوپن محلی یا وضعیت پرداخت UI مبنای قطعی سفارش نباشد. callback پرداخت و ثبت سفارش تکراری باید در backend کنترل شوند.

۴. پس از جایگزینی هر حوزه، دمو همان حوزه را از مسیر runtime خارج کنید و تست قرارداد، خطا، دسترسی و دادهٔ خالی اجرا کنید. endpoint تأیید ایمیل ساخته شده، اما ساخت/ورود حساب و دیتابیس هویت هنوز عملیاتی نیستند.

# Sales-plan API adapter

برای قابلیت طرح‌های فروش، `ISalesPlanSource` مرز منبع داده و `DemoSalesPlanSource` adapter فقط‌خواندنی fixture است. APIهای quote و validate-cart در `SalesPlansController` قیمت، انتخاب ویژگی و متعلقات را از دادهٔ سرور بازسازی می‌کنند. پیاده‌سازی به دیتابیس/رزرو موجودی و ثبت سفارش وصل نیست؛ وضعیت جزئی و کارهای باقی‌مانده در [راهنمای طرح‌های فروش](../store/sales-plans.md) ثبت شده است.

## یادداشت معماری آینده: مرز انبار و فروشگاه — ۷ نوامبر ۲۰۲۶

این بخش فقط ثبت نیاز اولیه برای طراحی آتی است؛ مدل، schema، API و پیاده‌سازی انبار هنوز طراحی یا ساخته نشده‌اند.

### نیاز فعلی

- سیستم باید چندشرکتی و چندانباری باشد؛ هر انبار در محدودهٔ شرکت خود شناسه و موجودی مستقل دارد.
- هر شرکت دقیقاً یک انبار فروش دارد. خود سایت به یک انبار فروش مشخص، متعلق به یک شرکت مشخص، متصل می‌شود و کاتالوگ فروشگاه موجودی را از همان انبار می‌خواند؛ دادهٔ چند انبار فروش با هم تجمیع نمی‌شود. اتصال باید صریح و قابل تشخیص/مدیریت باشد؛ جزئیات تغییر شرکت/انبار متصل و زمان اثرگذاری آن هنوز در طراحی باز است.
- موجودی قابل‌نمایش سایت از انبار فروش با این قاعده محاسبه می‌شود: `موجودی قابل‌نمایش = موجودی انبار − کف موجودی احتیاطی − مقدار سفارش‌های مؤثر در موجودی`. کف موجودی یک ذخیرهٔ احتیاطی است که به‌ازای هر شرکت و هر انبار، برای خود کالاهای بدون ویژگی و برای تک‌تک ویژگی‌های کالای ویژگی‌دار جدا ثبت می‌شود؛ مقدار پیش‌فرض آن برای همهٔ ردیف‌ها صفر است. وضعیت‌های سفارش فعلی عبارت‌اند از «در انتظار پرداخت»، «تأیید پرداخت»، «تأیید انبار»، «در حال ارسال»، «ارسال شد به پست»، «تحویل‌شده» و «لغوشده». پرچم `IsEffectiveInInventory = 1` روی وضعیت سفارش مشخص می‌کند که تعداد آن سفارش برای مشتری رزرو شده و تا زمان خروج فیزیکی از انبار باید از موجودی قابل‌نمایش کسر شود؛ وضعیت‌هایی با مقدار صفر در این کسر وارد نمی‌شوند. نگاشت هر وضعیت به این پرچم و زمان دقیق تغییر آن در چرخهٔ سفارش باید در طراحی قرارداد شود.
- کالا دو حالت دارد: بدون ویژگی، با یک ردیف موجودی برای خود کالا؛ یا ویژگی‌دار که موجودی هر ویژگی/گونه جداگانه ثبت و محاسبه می‌شود. در نمایش فروشگاه تعداد باقی‌مانده لزوماً آشکار نمی‌شود؛ اگر حاصل موجودی قابل‌نمایش برای کالا/ویژگی صفر یا کمتر باشد، نمایش «ناموجود» کافی است.
- محصول و تعریف ویژگی‌ها مرجع مشترک فروشگاه و انبار دارند؛ هیچ‌کدام تعریف موازی محصول یا ویژگی را برای خود ثبت نمی‌کنند. انبار برای موجودی به شناسهٔ مشترک محصول و در کالای ویژگی‌دار به شناسهٔ مشترک هر ویژگی/گونه ارجاع می‌دهد.
- اگر کالا ویژگی‌دار باشد، باید ویژگی/گونهٔ پیش‌فرض با `IsDefault` داشته باشد تا مدیریت فروشگاه قیمت نمایشی فهرست‌ها را از آن انتخاب کند. این پرچم صرفاً برای نمایش/قیمت فروشگاه است و بر مقدار یا محاسبهٔ موجودی انبار اثری ندارد؛ موجودی انبار برای همهٔ ویژگی‌های کالا، نه فقط ویژگی پیش‌فرض، جداگانه ثبت می‌شود.
- گردش انبار بر پایهٔ رسید و حواله با ردیف‌های کالا باشد؛ هر ردیف به محصول و در صورت نیاز ترکیب ویژگی‌های همان محصول ارجاع دهد.
- هر تراکنش رسید یا حواله به دقیقاً یک شرکت و یک انبار تعلق دارد. «رسید» و «حواله» نوع‌های اصلی سند هستند و هرکدام نوع‌های فرعی تعریف‌پذیر دارند؛ نمونه‌های فعلی رسید: «ابتدای دوره»، «اصلاحی» و «خرید»؛ نمونه‌های حواله: «فروش» و «تعدیل». این فهرست نمونه است و باید در طراحی تعیین شود که انواع توسط مدیر قابل تعریف‌اند یا از فهرست کنترل‌شده انتخاب می‌شوند.
- تعریف ویژگی و گزینه‌های محصول باید با کاتالوگ فروشگاه قابل تطبیق باشد تا موجودی برای گونهٔ درست کالا نگهداری شود. شناسهٔ مشترک محصول/گونه، سیاست کالاهای بدون ویژگی، واحد سنجش و رفتار کالای سریال‌دار هنوز تصمیم‌گیری نشده‌اند.
- قیمت‌گذاری کاملاً بیرون از دامنهٔ انبار است و در مدیریت فروشگاه انجام می‌شود. سند انبار نباید قیمت فروش، تخفیف یا محاسبهٔ مبلغ کالا را مالک شود؛ در اتصال بعدی، اگر گردش مالی سند لازم شد، واحد و مرجع مبلغ باید جداگانه تعریف شود.

### مرز مسئولیت پیشنهادی برای ادامهٔ طراحی

| انبار | فروشگاه / مدیریت فروش |
|---|---|
| شرکت، انبار و تنظیم اتصال انبار فروش | قیمت پایه، قیمت طرح و تخفیف |
| رسید، حواله و اقلام هر سند | نام/شرح و محتوای بازاریابی محصول |
| ارجاع به محصول/ویژگی مرجع مشترک و نگهداری موجودی هر شناسه | نمایش کاتالوگ و انتخاب خرید |
| موجودی فیزیکی و گردش افزایشی/کاهشی | تصمیم قیمت نهایی و پیش‌فاکتور |
| محاسبه و ارائهٔ موجودی قابل‌نمایش از انبار متصل، کسر حداقل کنترلی و رزرو سفارش‌های مؤثر | قیمت پایه، قیمت طرح، تخفیف و تغییر وضعیت سفارش |

این جدول مرزبندی مفهومی است، نه قرارداد نهایی: ثبت فروش، رزرو، برگشت، اصلاح موجودی، تجمیع چند انبار و هم‌زمانی درخواست‌ها باید پیش از ساخت API تعیین شوند. برای جلوگیری از وابستگی متقابل، اتصال آینده بهتر است از شناسه‌های پایدار محصول/گونه و یک قرارداد موجودی صریح استفاده کند؛ انبار نباید مدل قیمت فروشگاه را بخواند.

### تصمیم‌های باز برای جلسهٔ طراحی

1. دامنهٔ شرکت و سند: هر رسید/حواله به یک شرکت و انبار تعلق دارد؛ باید مشخص شود کاربر مدیریتی چطور شرکت فعال را انتخاب می‌کند و نوع‌های فرعی رسید/حواله آزادانه تعریف می‌شوند یا فهرست کنترل‌شده‌اند.
2. اتصال فروشگاه: یک انبار فروشِ متعلق به یک شرکت منبع یگانهٔ موجودی سایت است؛ باید تعیین شود تغییر انبار متصل چه مجوز، تأیید و زمان اثرگذاری‌ای دارد.
3. کف موجودی احتیاطی مشخص شد: در هر شرکت/انبار به‌ازای کالای بدون ویژگی یا هر ویژگی جداست و پیش‌فرض آن صفر است. در طراحی باید فقط قاعدهٔ جلوگیری از مقدار منفی و اثر مقدار کف بر هشدار/نمایش فروش بررسی شود.
4. اسناد: رسید/حواله چه وضعیت‌هایی دارند و آیا ثبت قطعی غیرقابل‌ویرایش است و برای اصلاح باید سند معکوس ساخت؟ انتقال بین دو انبار سند جفتی است یا حواله و رسید مستقل؟
5. ویژگی کالا: محصول و ویژگی‌ها مرجع مشترک‌اند و انبار شناسه‌های همان مرجع را استفاده می‌کند؛ دیگر تعریف موازی لازم نیست. باید روشن شود در صورت تغییر یا غیرفعال‌شدن ویژگی پس از ثبت گردش، تاریخچه و موجودی آن چگونه نگهداری شود.
6. ثبت فروش: در زمان افزودن به سبد، پیش‌فاکتور یا ثبت سفارش موجودی رزرو می‌شود؟ لغو/انقضا و مرجوعی موجودی را با چه سندی برمی‌گردانند؟
7. کنترل موجودی: شمارش دوره‌ای و سند تعدیل لازم است؟ چه نقش‌هایی مجاز به ثبت، تأیید و نهایی‌سازی هستند و سابقهٔ تغییرات چه جزئیاتی دارد؟
8. هم‌زمانی و خرابی: فروشگاه هنگام قطع سرویس انبار موجودی آخرین snapshot را نشان می‌دهد، فروش را می‌بندد یا از سیاست دیگری پیروی می‌کند؟

تا وقتی این پرسش‌ها بررسی نشده‌اند، این یادداشت را نیاز اولیه بدانید و از استخراج schema یا افزودن مدل‌های نمونه در Shop خودداری کنید. وقتی طراحی شروع شد، ابتدا مرزهای چندشرکتی، سندها، شناسهٔ گونه، رزرو و قرارداد read/write موجودی را نهایی کنید؛ سپس منبع داده و آزمون‌های قرارداد مستقل را طراحی کنید.
